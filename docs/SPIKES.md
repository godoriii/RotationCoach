## S1. 로그 기록 지연과 뭉침 측정

**목적**: 한밤 12.x에서 전투 로그가 언제, 어떤 묶음으로 파일에 쓰이는지 측정해 (1) "풀 종료 직후 표시"가 가능한 지연인지, (2) 전투 중 데이터가 들어오는지(D-3), (3) 큰 배치의 크기(성능 요구)를 확정한다.

**배경**: 10.2부터 전투 종료 시 일괄 기록된다는 보고 [2차 B-1, B-2], 레이드 밖에서는 이벤트가 쌓여야 기록된다는 예전 설명 [B-7b], "수 분" 지연 보고 [B-3]. 모두 한밤 12.x 실측은 아니다.

**범위**
- 하는 것: 파일 크기 변화 감시와 기록 시각 측정, 줄 타임스탬프와 도착 시각 비교, 배치 크기·순서 뒤섞임 측정
- 안 하는 것: 이벤트 의미 파싱(S2 몫), 기록을 앞당기려는 어떤 조작도 하지 않음 (C-6)

**도구**: `spikes/s1_log_latency.py` — 약 150줄 Python, 표준 라이브러리만.
- `Logs` 폴더를 20 ms마다 확인해 최신 `WoWCombatLog*.txt`의 새 바이트를 읽고, 읽은 묶음마다 `도착 시각, 바이트 수, 줄 수, 묶음 안 첫·마지막 로그 타임스탬프, 역순 줄 수`를 CSV로 남긴다.
- 사용자가 전투 시작·종료 시점에 콘솔 창에서 Enter로 표시(마커)할 수 있다. 게임 안에서는 아무것도 하지 않는다.
- 같은 PC 시계이므로 `지연 = 도착 시각 − 줄 타임스탬프`로 계산한다 (로그 타임스탬프 정밀도 1 ms).

**절차**

| 시나리오 | 내용 | 반복 |
|---|---|---|
| A. 도시 허수아비 | 60 s 공격 → 전투 이탈 → 30 s 대기 | 3회 |
| B. 허수아비 장시간 | 5분 공격 (배치 크기, 전투 중 기록 여부) | 1회 |
| C. 인스턴스 (추종자 던전 등) 보스 1 | 보스 전투 1회 + 잡몹 1구간 | 1회 |
| D. 레이드 보스 (가능하면 공격대 찾기 이상) | 보스 전투 1회 | 1회 |
| E. 전투 중 `/reload` | 허수아비 30 s 후 `/reload` → 손실 여부 | 1회 |

**측정 지표**
- 전투 중 도착한 줄의 비율 (0이면 일괄 기록 확정)
- **전투 종료 → 해당 전투 마지막 줄 도착** 지연 (p50/p95/최대)
- 배치당 줄 수·바이트, 5분 레이드 풀의 총 줄 수 (T-13 성능 요구 근거)
- 배치 안 역순 줄 비율과 최대 역순 폭(ms)
- 시나리오 E의 데이터 손실 여부

**성공 기준 (판정)**

| 결과 | 판정 | 다음 행동 |
|---|---|---|
| 전투 종료 → 도착 p95 ≤ 3 s (A, C, D 모두) | 풀 종료 직후 모드 **확정** | M1 진행 |
| 일부 콘텐츠만 3–30 s | 조건부 확정 | 그 콘텐츠는 "데이터 대기 중" 표시 |
| 어디서나 30 s 초과 또는 수 분 | 오버레이 가치 하락 | 제품을 "세션 리뷰(제어판 중심)"로 전환할지 사용자와 재논의 |
| 전투 중 도착 비율 ≈ 0 | 전투 중 갱신 불가 | D-3 → 전투 중 갱신 미구현 추천 |
| 전투 중 도착이 의미 있게 있음 | 기술적으로 가능 | D-3은 정책 판단으로 결정 (RISKS P-1) |

**산출물**: `spikes/results/S1.md` (표·그래프), 원본 CSV (로컬).

## S2. 생존 사냥꾼 핵심 상태를 로그만으로 재구성할 수 있는가

**목적**: 채점에 필요한 상태(버프·자원·쿨다운·영웅 특성 요소)가 로그에 어떻게 나타나는지 실측하고, 각 요소를 관측(O)/추론(I)/불확정(U)/불가(X)로 확정한다 ([SCORING_SPEC §6.1](SCORING_SPEC.md#61-요소별-처리-방침)의 [미확인] 항목 해소).

**범위**
- 하는 것: 녹화 로그에서 대상 주문·오라 ID 출현 여부, 고급 블록 필드 수와 각 필드 의미, 집중 관측 지점, 시전 실패 사유 문자열(한국어), `COMBATANT_INFO` 특성 파싱, 펫·야수 소환 기록, 쿨다운 모델 오차
- 안 하는 것: 판정·점수 (M3 몫)

**녹화 절차** (🧑, 각 영웅 특성 빌드로 1회씩, S1과 같은 세션에서 가능)

| 단계 | 내용 | 확인 대상 |
|---|---|---|
| 1 | 허수아비 3분 평소 로테이션 | 전체 목록 |
| 2 | Kill Command만 연타 30 s (충전 소진 후 회복 대기) | 충전 2개·5 s(가속 적용) 모델 |
| 3 | Wildfire Bomb을 쿨이 돌아올 때마다 바로 사용 (키를 반복해서 눌러도 됨) 60 s | 감소 효과 연쇄 모델 오차, 실패 사유 이벤트 |
| 4 | Boomstick 정신 집중 중 이동해 보기 1회 | 정신 집중 끊김, 종료 이벤트 |
| 5 | 허수아비에서 사거리 밖으로 나가 Raptor Strike 시도 | 사거리 실패 사유, 위치 필드 |
| 6 | 던전 또는 레이드 보스 1회 | `COMBATANT_INFO`(특성·가속), 전투 경계 |

**분석 도구**: `spikes/s2_inventory.py` — 로그를 읽어 아래 체크리스트 표를 자동 생성. 쿨다운은 "최대 가능 충전 시간"(그보다 길면 0충전에서 시전한 셈이 되는 최댓값)을 이분 탐색으로 구해 명목값/(1+가속)과 비교한다. 이 값은 **상한**이다: 준비 즉시 누르지 않은 시전이 섞이면 실제보다 커진다 (합성 로그 검증: Kill Command는 정확, Wildfire Bomb은 +0.28 s). 그래서 단계 2–3에서 "준비되면 바로" 누르는 것이 중요하다.

**체크리스트 (발췌)**

| 요소 | 확인 내용 |
|---|---|
| 고급 블록 | 필드 수(17 vs 19), 각 필드 값 범위, `SPELL_CAST_SUCCESS`의 블록이 시전자인지 |
| 집중 | 어떤 이벤트에서 플레이어 집중이 보이는가, 비용 차감 전/후 |
| Tip of the Spear (260286) | `APPLIED_DOSE`/`REMOVED_DOSE` 기록, 최대 3 |
| Raptor Swipe! (1273155), Raptor Swipe 시전 (1262293) | 발동 오라 기록 |
| Takedown 버프 (1250646), Moonlight Chakram 창 (1264946) | 오라 기록 |
| Howl 준비 버프 (471878/472324/472325), 주기 오라 (471877) | 무리의 지도자 빌드에서 기록 여부 |
| Sentinel's Mark (1253601) | 파수꾼 빌드에서 목표 디버프 기록 |
| Grenade Juggler (470488), Wildfire Imbuement (1252947), Wallop (1252741) | 오라 기록 |
| 야수 소환 (Wyvern/Boar/Bear) | `SPELL_SUMMON`, 소유자 |
| Boomstick (1261193 / tick 1261215) | 정신 집중 시작·틱·종료 |
| `SPELL_CAST_FAILED` | 자신의 실패만 기록되는지, 한국어 사유 문자열 목록 |
| `COMBATANT_INFO` | 허수아비에서는 없는지, 보스 전투에서 특성 `(nodeId, entryId, rank)` 파싱 |

**성공 기준**
- 단일 대상 APL(`plst`, `sentst`)이 쓰는 표현식 항의 **90% 이상이 O 또는 I**로 분류됨. 나머지는 U로 처리 방침이 정해짐.
- Kill Command 충전 모델: 예측 준비 시각 오차 p95 ≤ 150 ms.
- Wildfire Bomb 모델: 3분 동안 예측 오차 p95 ≤ 300 ms (단계 3 기준).
- 고급 블록 레이아웃과 집중 관측 지점 확정.
- 실패 시: 해당 요소를 U로 두고 INDETERMINATE 비율 추정치를 SCORING_SPEC에 반영. 90%에 못 미치면 MVP 판정 범위(어떤 줄을 채점할지)를 줄이는 안을 제시.

**산출물**: `spikes/results/S2.md` (관측성 표 확정본), 익명화한 샘플 로그 2–3개 → M1·M2 회귀 테스트 고정 데이터.

## S3. 창 모드(전체 화면) WoW 위 클릭 통과 오버레이

**목적**: PySide6 최소 오버레이가 WoW "창 모드(전체 화면)" 위에서 요구 동작을 모두 만족하고 성능 영향이 없는지 확인한다 (D-1).

**도구**: `spikes/s3_overlay.py` — 약 120줄. 반투명 패널에 시계·카운터를 1 Hz로 갱신해 표시. [TECH_DECISIONS §2.3](TECH_DECISIONS.md#23-구현-메모-본-구현-시)의 플래그 + `ctypes` 확장 스타일 + 2 s 최상위 재설정. 게임과는 아무 상호작용 없음.

**확인 항목**

| # | 항목 | 통과 조건 |
|---|---|---|
| 1 | 표시 | WoW 위에 보임 (창 모드(전체 화면), 창 모드 둘 다) |
| 2 | 클릭 통과 | 오버레이 영역에서 좌클릭 대상 지정, 우클릭 드래그 카메라 회전, 휠 줌이 모두 게임에 전달됨 |
| 3 | 포커스 | 오버레이 갱신 중 채팅 입력이 끊기지 않음. 오버레이 실행·갱신 시 WoW가 포커스를 잃지 않음 |
| 4 | Alt-Tab | Alt-Tab 목록·작업 표시줄에 오버레이가 없음 |
| 5 | 최상위 유지 | Alt-Tab으로 나갔다 돌아온 뒤, Discord 오버레이 등 다른 최상위 창이 있을 때도 보임 |
| 6 | 성능 | PresentMon으로 같은 장소 2분 × 3회 (오버레이 있음/없음): 평균 FPS 하락 ≤ 1%, 1% low 하락 ≤ 2% |
| 7 | 표시 모드 | PresentMon의 PresentMode 기록 (Hardware Independent Flip ↔ Composed 전환 여부) |
| 8 | DPI | 배율 100%·150%에서 위치·크기 정상 |
| 9 | 다중 모니터 (해당 시) | 지정한 모니터에 표시 |

**성공 기준**: 1–5, 8 모두 통과 + 6 기준 충족.
**실패 시**: 2–4 실패 → Win32 스타일 직접 생성으로 재시도 → 그래도 실패하면 Electron 최소 오버레이로 같은 항목 측정 (별도 승인). 6 실패 → 갱신 주기·창 크기 축소, 그래도 안 되면 "보조 모니터 모드"를 기본으로.

## S4. SimC APL 파싱과 표현식 항 목록

**목적**: 고정 커밋의 생존 APL을 프로토타입 파서로 100% 파싱하고, 쓰이는 모든 표현식 항을 관측성 분류와 함께 목록화한다 (D-2 근거).

**범위**: 파서·3값 평가기 프로토타입(상태는 가짜 값), 항 목록 생성. 실제 로그 연결은 하지 않음.
**도구**: `spikes/s4_apl_parse.py` — 이 클라우드 환경에서 수행 가능.

**성공 기준**
- `hunter_survival.simc` @ `76f8118c` 전체 줄 파싱 오류 0.
- 연산자 우선순위가 SimC 위키 정의와 일치 (위키 문구 확인 포함, [TECH_DECISIONS §3.3](TECH_DECISIONS.md#33-혼합안-세부)).
- 항 목록 표: 항, 사용 목록, 관측성(O/I/U/X), 구현 위치(코어/스펙 어댑터).
- 직전 TWW APL에도 돌려 "확장 시 필요한 구문"(variable, run_action_list 등)을 함께 목록화.

## S5. WCL API v2 연동과 이벤트 동등성

**목적**: WCL 인증·쿼리·요청 한도 비용을 실측하고, 같은 풀의 로컬 로그와 WCL 이벤트가 같은 정규화 결과를 내는지 확인한다 (NFR-A8).

**사전 준비 (🔑 사용자)**: warcraftlogs.com에서 API 클라이언트 생성(client credentials), S2 6단계 로그를 WCL에 unlisted로 업로드, client id/secret을 자격 증명 관리자에 저장(스크립트가 안내).

## S8. SimC 골든 데이터로 APL 인터프리터 검증

**목적**: 상태를 정확히 아는 조건에서 우리 APL 인터프리터가 SimC와 같은 행동을 고르는지(NFR-A4 ≥ 98%), 그리고 상태 재구성기가 관측 가능한 이벤트만으로 SimC 내부 상태를 얼마나 따라가는지 검증한다.

**방법**
1. 이 환경에서 simc(`midnight` @ 고정 커밋)를 빌드한다 (C++ 컴파일, 시간 소요).
2. `profiles/MID2/MID2_Hunter_Survival.simc` 기반으로 무리의 지도자·파수꾼 각각 단일 대상 300 s, `log=1`로 실행해 행동 로그를 얻는다.
3. **8a 인터프리터 검증**: 시뮬 로그의 상태(버프·쿨다운·충전)를 그대로 넣었을 때 우리 인터프리터의 top = SimC가 실행한 행동인지 비교.
4. **8b 재구성 검증**: 시뮬 로그를 "전투 로그에서 보일 이벤트만" 남기도록 변환해 상태 재구성기 → 인터프리터 경로로 비교. 차이는 숨은 상태 모델 오차로 분류.

**성공 기준**: 8a ≥ 98% 일치 (불일치는 모두 원인 설명). 8b의 불일치가 INDETERMINATE로 잡히거나 원인이 분류됨.
**주의**: SimC `log=1` 출력 형식이 이 변환에 충분한지는 [미확인] → 첫 단계에서 확인하고, 부족하면 `report_details`/JSON 출력으로 대체.

## S9. 판정 규칙 보정 (수동 라벨)

**목적**: 엔진 판정이 생존 사냥꾼을 잘 아는 사람(사용자)의 판단과 맞는지 확인하고 허용 오차(R, δ, Q), 동률 그룹, 경미 쌍, 가중치를 조정한다 (NFR-A5 ≥ 90%).

**시점**: M3 초기 엔진이 나온 뒤.
**방법**: 3개 풀(무리의 지도자 허수아비, 파수꾼 허수아비, 레이드 보스 1)에서 DP 약 300개를 제어판의 간단한 라벨 화면(엔진 판정을 가린 상태)으로 사용자가 "맞음/허용/실수/모르겠음" 표시 → 엔진 판정과 혼동 행렬 비교 → 불일치 사례별 원인(규칙/상태/APL) 분류 → 규칙 조정 → 재측정.
**성공 기준**: 판정 가능 DP에서 일치 ≥ 90%, "사람은 실수라는데 엔진은 MATCH" 사례 원인 100% 설명.
